# Activity 2: "Build the Event Loop" - Physical Simulation

## Questions

**1. What happened to the other events while you were "stuck" on the slow handler?**
They just waited in the event queue. Nothing was lost, but none of the other cards could be processed until the slow handler finished, because the event loop handles one event at a time.

**2. What would a user see if this happened in a real application?**
The application would appear frozen or "Not Responding". Buttons would not react, the window could not be moved or redrawn properly, and the user's clicks would pile up in the queue and all fire at once when the slow handler finally finished.

**3. How could this problem be fixed?**
Move long-running work (network calls, file I/O, heavy calculations) off the event loop into a background thread, and only come back to the event thread to update the GUI (e.g. `SwingUtilities.invokeLater()` or `SwingWorker` in Java Swing).

## Reflection

The event queue is a first-in-first-out line that holds events (clicks, key presses, timer ticks) generated by event sources until the application is ready to handle them. The event loop is the process that continually checks the queue, takes the next event, and runs the handler (callback) associated with it before repeating. Because the loop runs handlers one at a time, each handler must finish quickly. If a handler takes a long time, the event loop is blocked and every other event has to wait, which makes the application freeze and look broken to the user. In Java Swing, this loop runs on the Event Dispatch Thread (EDT), so slow work must be moved to background threads. Keeping the event loop free is what lets a GUI feel responsive and handle many different user actions in any order.
